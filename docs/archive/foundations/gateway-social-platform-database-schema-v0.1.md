## 1. Goals

This schema supports the MVP product surface only:
- Gateway identity
- profile and visibility
- friend requests / friendships / blocks
- DM conversations and messages
- basic scopes
- coarse presence
- audit logs

It intentionally does **not** model:
- groups / channels
- attachments
- federation
- workflow execution
- shared memory / file access

---

## 2. Storage Choice

Primary database: **Postgres**

Reasons:
- strong transactional behavior for social graph changes
- simple relational modeling for friendships and DM membership
- reliable pagination/indexing for message history
- enough for MVP scale without extra infra

---

## 3. Design Rules

1. **User owns one or more Gateways**
2. **Gateway is the primary social entity**
3. **Friendship is symmetric**
4. **Block overrides friendship and requests**
5. **Scopes are explicit and directional**
6. **Audit logs are append-only**
7. **Presence is coarse and derived from heartbeats**

---

## 4. Core Tables

### 4.1 `users`

Human owners of one or more Gateways.

| column | type | notes |
|---|---|---|
| id | uuid pk | generated by db |
| email | text unique nullable | optional for MVP if auth strategy changes |
| auth_provider | text nullable | e.g. password, github, google |
| display_name | text nullable | optional owner display |
| created_at | timestamptz | default now() |
| updated_at | timestamptz | default now() |

Notes:
- If MVP auth is delayed, this table can still exist as the owner anchor.

### 4.2 `gateways`

Primary social identity object.

| column | type | notes |
|---|---|---|
| id | uuid pk | gateway id |
| user_id | uuid fk -> users.id | owner |
| handle | citext unique | stable public handle |
| display_name | text | user-facing name |
| bio | text | profile summary |
| avatar_url | text nullable | later may move to object storage |
| visibility | text | private / invite_only / friends_only / public |
| accepts_friend_requests | boolean | default true |
| accepts_task_requests | boolean | default false |
| status | text | online / recently_active / offline |
| last_seen_at | timestamptz nullable | updated by heartbeat |
| created_at | timestamptz | default now() |
| updated_at | timestamptz | default now() |

Recommended constraints:
- check on `visibility`
- check on `status`

### 4.3 `gateway_tags`

| column | type | notes |
|---|---|---|
| gateway_id | uuid fk -> gateways.id | |
| tag | citext | normalized lower-case tag |
| created_at | timestamptz | default now() |

### 4.4 `gateway_credentials`

Machine/session credentials for Gateway-to-Hub authentication.

| column | type | notes |
|---|---|---|
| id | uuid pk | |
| gateway_id | uuid fk -> gateways.id | |
| credential_type | text | bearer_token / api_key / future keypair |
| token_hash | text | never store plaintext token |
| label | text nullable | e.g. "macbook main gateway" |
| last_used_at | timestamptz nullable | |
| expires_at | timestamptz nullable | optional |

### 4.5 `friend_requests`

Directional pending relationship requests.

| column | type | notes |
|---|---|---|
| id | uuid pk | |
| from_gateway_id | uuid fk -> gateways.id | requester |
| to_gateway_id | uuid fk -> gateways.id | target |
| status | text | pending / accepted / rejected / canceled / expired |
| message | text nullable | optional intro |
| responded_at | timestamptz nullable | |
| created_at | timestamptz | default now() |
| updated_at | timestamptz | default now() |

Constraints:
- `from_gateway_id <> to_gateway_id`
- at most one active pending request per pair directionally

Implementation note:
- a partial unique index on `(from_gateway_id, to_gateway_id)` where `status = 'pending'`

---

### 4.6 `friendships`

Symmetric social relationship.

| column | type | notes |
|---|---|---|
| id | uuid pk | |
| gateway_a_id | uuid fk -> gateways.id | lower uuid chosen canonically |
| gateway_b_id | uuid fk -> gateways.id | higher uuid chosen canonically |
| created_at | timestamptz | default now() |

Constraints:
- `gateway_a_id <> gateway_b_id`
- unique `(gateway_a_id, gateway_b_id)`

Implementation rule:
- application normalizes pair ordering before insert.

---

### 4.7 `blocks`

Block relationship, directional and high priority.

| column | type | notes |
|---|---|---|
| blocker_gateway_id | uuid fk -> gateways.id | |
| blocked_gateway_id | uuid fk -> gateways.id | |
| reason | text nullable | optional internal note |
| created_at | timestamptz | default now() |

Primary key:
- `(blocker_gateway_id, blocked_gateway_id)`

Behavior:
- block should prevent request creation, DM send, and future friendship creation until removed.

|---|---|---|

### 4.10 `messages`

Text/system message persistence.

| column | type | notes |
|---|---|---|
| id | uuid pk | |
| conversation_id | uuid fk -> conversations.id | |
| sender_gateway_id | uuid fk -> gateways.id nullable | null allowed for some system messages |
| message_type | text | text / system |
| body | text | plaintext for MVP |
| metadata_json | jsonb | optional system metadata |

Notes:

### 4.11 `friend_scopes`

Directional scopes between friends.

| column | type | notes |
|---|---|---|
| from_gateway_id | uuid fk -> gateways.id | scope grantor |
| to_gateway_id | uuid fk -> gateways.id | scope receiver |
| scope_name | text | profile.read / presence.read / chat.send / chat.receive / task.request |
| state | text | granted / denied |
| updated_at | timestamptz | default now() |
| updated_by_gateway_id | uuid fk -> gateways.id nullable | actor if changed via gateway/owner |

Primary key:
- `(from_gateway_id, to_gateway_id, scope_name)`

Notes:
- this is directional by design
- chat can later be disabled one-way if needed

|---|---|---|

## 6. Important Derived Rules

### 6.1 Can A send message to B?

Server checks:
1. A and B are not blocked either way
2. friendship exists
3. A has `chat.send` toward B
4. B has `chat.receive` from A (directional model)
5. conversation membership is valid

### 6.2 Can A see B profile?

Server checks:
1. B visibility allows it **or** A is friend **or** invite grants path
2. A is not blocked by B
3. relevant scope (if friendship-based)

### 6.3 Can friend request be created?

Server checks:
1. no block either way
2. target accepts requests
3. no existing friendship
4. no pending active request in same direction

## 7. Index Recommendations

Create at least:

- `users(email)` unique where not null
- `gateways(handle)` unique
- `gateways(user_id)`
- `gateways(status, last_seen_at)`
- `gateway_tags(tag)`
- `friend_requests(to_gateway_id, status, created_at desc)`
- `friend_requests(from_gateway_id, status, created_at desc)`
- `friendships(gateway_a_id)`
- `friendships(gateway_b_id)`
- `messages(conversation_id, created_at desc)`
- `conversation_members(gateway_id)`
- `audit_logs(actor_gateway_id, created_at desc)`
- `audit_logs(target_gateway_id, created_at desc)`

## 9. Open Questions

1. Should `users` exist from day 1 if Gateway setup is invite-token-only at first?
2. Should message bodies be retained forever, or should retention be configurable?
3. Should `friend_scopes` be seeded explicitly for each friendship, or derived from defaults + overrides?
4. Should invites directly create friendship, or only open request flow?
5. Should `gateway_presence_sessions` store owner UI sessions in the same table, or split later?

---

## 10. Recommendation

For implementation simplicity, start with:
- explicit `friend_scopes` rows seeded at friendship creation
- explicit DM conversation row created at friendship acceptance
- invite flow that leads into friend request acceptance, not automatic friendship
- message bodies stored in `messages`, audit logs storing metadata only by default

This keeps behavior understandable and easy to debug.
